# CLAUDE.md

## Project Overview

ClawHuddle is a multi-tenant platform for managing OpenClaw AI gateway instances. Each org member runs one or more personal OpenClaw Docker containers ("instances", rows in `gateways`, numbered by `slot`) with auto-provisioned config, credentials, and skills. How many a member may run is `org_members.max_gateways` → `organizations.max_gateways_per_user` → `MAX_GATEWAYS_PER_USER` (default 1). Skills and API keys are per user and shared by all of a member's instances; channel bot tokens (`gateway_channels`) and the primary-provider pin are per instance. An instance's runtime is `gateways.runtime`: `openclaw` (default; everything below is about it unless it says Hermes) or `hermes` (Hermes Agent, see "Hermes runtime"), offered at "New instance" only while the org's `hermes_enabled` switch is on.

## Architecture

```
Monorepo
├── apps/api          Fastify + SQLite backend (dockerode for container management)
├── apps/web          Next.js 16 frontend (NextAuth v5)
├── packages/shared   Shared types, provider definitions
└── vendor/claw-proxy Git submodule — OpenAI-compatible proxy for Claude Max
```

**Data flow**: Frontend → API server → generates `openclaw.json` + `auth-profiles.json` → mounts into per-user Docker containers → OpenClaw gateway reads config on startup.

## API Authentication

The API never trusts a client-supplied user id. Both apps share `API_AUTH_SECRET` (≥ 32 chars; the API refuses to start without it) and use the HS256 helpers in `packages/shared/src/api-token.ts`:

- **User tokens** (`aud: 'user'`, 1h): minted in NextAuth's `jwt` callback (`apps/web/lib/auth.ts`), re-minted when < 15 min remain, exposed as `session.apiToken`. `apiFetch` (`apps/web/lib/api.ts`) attaches it as `Authorization: Bearer …` and retries once after refreshing the session on a 401. `authPlugin` verifies it.
- **Internal tokens** (`aud: 'internal'`, 60s): the web server's calls to `/api/auth/login` and `/api/auth/check-access`, guarded by `requireInternal`. These routes return any user's id by email, so they must never be reachable without one.
- A gateway's `token` is a bearer credential: it is only returned by `GET /me/gateways` for the caller's own instances. Admins get another member's one at a time from `GET /api/orgs/:orgId/gateways/:gatewayId/access` (logged; admins can't open an owner's gateway, owners can open any). Members act only on their own instances; `requireGatewayAccess` in `routes/org/gateways.ts` enforces it.

## Security Invariants

- Device pairing: `docker/gateway/entrypoint.sh` still auto-approves pending device requests every 5 s (kept on purpose). The web app's Device Requests page (`GET /me/device-requests`, admin `GET /device-requests`, `POST /gateways/:gatewayId/devices/:requestId/{approve,reject}` → `openclaw devices …` exec'd in the container) is the manual path; it only sees a request in the window before the loop approves it, or on a container where the loop is off. `openclaw devices list` costs ~4.5 CPU-seconds a run, so both the loop and `listDeviceRequests` first ask `clawhuddle-pending-devices` (`docker/gateway/pending-devices.cjs`), which counts unexpired rows in `device_pairing_pending` in OpenClaw's state database, and only run the CLI when the answer is not exactly 0. It reads an OpenClaw internal: on any error it prints nothing and callers fall back to the CLI, and an instance on an older image falls back the same way (exec exits 127). After an OpenClaw upgrade, check the table and `DEVICE_PAIRING_PENDING_TTL_MS` still match; a broken check costs CPU, not approvals.
- State lock (OpenClaw 2026.11.5+): a gateway that was killed leaves its lock in `tmp/openclaw-0/`, and neither a new gateway nor any state-using CLI ever takes over a lock whose owner is in a PID namespace it cannot inspect, which is every owner from an earlier start of the container ("cannot verify Gateway ownership … will not be reclaimed automatically"; on 11.2 it simply expired after 90 s). Two things in the gateway image keep that from stranding an instance: the entrypoint passes SIGTERM on to the gateway, so `docker stop` is a clean shutdown (~1 s when idle) that releases the lock, and it runs `clawhuddle-recover-lock` (`docker/gateway/recover-state-lock.sh`: `openclaw gateway recover-lock --json`, then `--confirm <fingerprint>`) before anything else touches the state. Only call the helper where the owner is known to be gone: at container boot, or from the key save's throwaway container while the instance is down. An instance whose OpenClaw was updated from inside the container (Control UI → Update) keeps its old image's entrypoint: redeploy it onto the current image.
- SSH keys for an instance live in its state dir (`~/.openclaw/ssh`: key, `config`, `known_hosts`), never in the workspace; the entrypoint links `~/.ssh` to it on every boot (only when `~/.ssh` doesn't exist), since `/root/.ssh` is not persisted. The OpenClaw secret store can't protect SSH keys (it only substitutes into HTTPS), so the agent can read the key: use a key dedicated to one instance and restrict it on the server (`from="<host IP>"`, low-privilege account).
- Gateways run agent-controlled code (and anyone who can message them can steer it). They live on `GATEWAY_NETWORK` (`clawhuddle-gateways`) with only Traefik and claw-proxy; the API and web stay on `clawhuddle-net`.
- Slack defaults to OpenClaw's own policy (`dmPolicy: pairing`, `groupPolicy: allowlist`, `allowBots: false`). `mergeOpenClawConfig` migrates blocks still carrying the old wide-open platform default; blocks the member changed are left alone. The migration runs once per gateway (`gateways.slack_access_migrated_at`), so a member can open Slack again — even to exactly the old default — and keep it across redeploys.
- Instance naming is in `services/gateway-store.ts`: slot 1 keeps the pre-instance container name `clawhuddle-gw-<org8>-<user8>` and data dir `data/gateways/<orgId>/<userId>`; slot N≥2 adds `-N` to both. `org_members.gateway_*` only mirror the slot-1 row (for rollback) — never read them. All `gateways` writes go through the store so the mirror stays right. `migrate.ts` re-runs every migration on each boot; one-shot backfills are guarded by `migration_marks` (see `020-gateways.sql`).
- Port-forward Traefik files are written with `JSON.stringify` (JSON is valid YAML) — never interpolate request input into them.
- Only owners can grant the owner role, including through invitations (checked when sent and again when accepted); roles and statuses are validated against fixed lists.
- Roles: `owner` > `admin` > `maintainer` > `member`. A maintainer sees only the Members page (`/admin`; other admin pages redirect), and `GET /members` returns them only `member` rows plus their own. They manage plain members' instances (deploy, start/stop/restart/redeploy, open via `/access`, channels, usage — but remove only their own instances; `canManageGatewaysOf` in `middleware/auth.ts`) but cannot invite, change roles, statuses or limits, see keys, or touch an admin's or owner's instance.

## Claw Proxy Integration

claw-proxy routes OpenAI-format requests through `claude -p` CLI using Claude Max subscriptions. It registers as a **custom OpenClaw provider** (not env var override).

### How it works

1. Admin adds bearer token via UI under "Claw Proxy (Claude Max)" provider — this alone enables proxy
2. On gateway provision/redeploy, `generateOpenClawConfig()` writes a `models.providers.claw` section into `openclaw.json` with:
   - `baseUrl` (default `http://claw-proxy:3456/v1`, override via `CLAW_PROXY_URL` env var)
   - `apiKey` (bearer token from DB)
   - `api: "openai-completions"`
   - Full model definitions (id, name, reasoning, contextWindow, cost=0)
3. Model IDs use `claw/` prefix (e.g. `claw/claude-sonnet-4-6`)
4. Bearer token goes into `openclaw.json` directly — NOT `auth-profiles.json`

### Key env vars

| Variable | Where | Purpose |
|----------|-------|---------|
| `CLAW_PROXY_URL` | API server `.env` | Optional override for claw-proxy base URL (default: `http://claw-proxy:3456/v1`) |

### Frontend behavior

- "Claw Proxy (Claude Max)" always visible as a provider card in Admin → API Keys
- Adding a bearer token is the only step needed to enable proxy — no env var required

### Starting claw-proxy

```bash
docker compose --profile proxy up -d --build
```

Config: `data/claw-proxy/config.json` (bearerToken + accounts with oauthTokens from `claude setup-token`).

## Token Kiosk Integration

Token Kiosk (internal OpenRouter-style gateway at `https://agent-router.gaib.ai/v1`, docs at `https://token-kiosk.gaib.ai/docs`) follows the same custom-provider pattern as claw-proxy:

1. Admin adds an `sk-...` key via UI under "Token Kiosk" provider
2. `generateOpenClawConfig()` writes a `models.providers.tokenkiosk` section into `openclaw.json` (baseUrl default `https://agent-router.gaib.ai/v1`, override via `TOKEN_KIOSK_URL` env var)
3. Model IDs use `tokenkiosk/` prefix plus the kiosk's own id — either a `<provider>/<model>` id (e.g. `tokenkiosk/azure/gpt-5.5`, `tokenkiosk/bedrock/kimi-k2.5`; the kiosk routes on its prefix) or one of the kiosk's rolling aliases (e.g. `tokenkiosk/claude-opus-latest`)
4. Key goes into `openclaw.json` directly — NOT `auth-profiles.json`

Curated models: Azure GPT-5.5 / GPT-5.6 Sol, AWS Bedrock Kimi K2.5 / K2 Thinking, Claude Opus (latest). The kiosk's full catalog is public at `GET /v1/models` (no auth) if more are wanted.

## Provider System

Providers are defined in `packages/shared/src/index.ts` as `PROVIDERS` array. Each has:
- `id`, `label`, `envVar`, `placeholder`, `defaultModel`
- `models[]` — available models (with optional `proxyOnly` flag)
- Optional: `supportsSetupToken`, `supportsOAuth`

API keys are stored in `api_keys` table (org-scoped), written to `auth-profiles.json` for standard providers, or embedded in `openclaw.json` for custom providers (claw-proxy, token-kiosk).

**Gateway image.** `clawhuddle-gateway:local` is OpenClaw 2026.11.10 since 2026-11-27 (rollback tag `:2026.11.2-final`). An instance moves to it at its next Redeploy; a Restart keeps its container and image. The first boot on 11.10 upgrades the state and agent databases one way (Doctor backs both up first as `*.pre-startup-migration-*.bak`; ~6 min for a 2.5 GB state dir, ~9 min until the gateway answers), so going back means restoring those backups, not just the old image. `docker compose build` without a service name rebuilds this image from `docker/gateway/Dockerfile` (and `clawhuddle-hermes:local` from `docker/hermes/Dockerfile`); name the service (`build api web`) when that is not the intent.

**How a changed key reaches an instance (OpenClaw 2026.11.x).** 11.x keeps auth profiles in the state database (`state/openclaw.sqlite`, `config_machine_state` row `authProfiles.store`), with the agent database's `auth_profile_store` as a per-agent layer on top, and Doctor no longer imports `auth-profiles.json` after an instance's first boot. So on every deploy, restart and start, while the container is down, `reconcileAuthProfileStore` (`services/gateway.ts`) compares each API key / setup token we mint (`<provider>:manual`, `:setup-token`) with the shared store and returns the ids it lacks, holds without a credential, or holds with another value; `saveAuthProfilesOffline` then saves each with OpenClaw's own CLI (`openclaw models auth paste-api-key|paste-token`, key on stdin from a transient 0600 file) in a throwaway `clawhuddle-authsave-…` container of the instance's own image, no network, ~5 s. Three things the CLI refuses on, all handled there: more than one agent in `agents.entries` ("Multiple agents are configured … Pass --agent <id>"; `authOwnerAgent` names the default agent, the key lands in the shared store either way), a not-yet-imported `auth-profiles.json` next to the agent store (`AUTH_PROFILE_MIGRATION_REQUIRED`; the file we just wrote is moved aside for the save and put back), and a killed gateway's state lock in `tmp/openclaw-0/*.lock` (see "State lock" below): on a 2026.11.10 image the save first runs `clawhuddle-recover-lock` (~12 s in all); on a 2026.11.2 image, which has no such helper, the lock stays valid for 90 s after its last heartbeat unless the throwaway container happens to get the dead container's PID namespace ("owner heartbeat is fresh … wait N s and retry"; we wait that long and retry, so the save can take ~95 s). The CLI only prints its reason with `OPENCLAW_DEBUG=1`, which the save sets. The save uses the image the instance last ran on (a redeploy passes the previous container's image, not the new one): the CLI of a newer OpenClaw refuses state its Doctor has not upgraded yet. Key changes never touch a running instance: they arrive at its next restart or redeploy. Never write or drop profiles in either store directly: nothing re-imports them (2026-11-23: the pre-11 "drop for re-import" rule deleted Michael's `google:manual` pointer and his agent lost Gemini). A profile with a `keyRef`/`tokenRef` in either store is the member's own and is left alone; a replaced OAuth credential is only reported in the API log. A failed save is logged and the instance boots on its previous credential.

**A replaced key un-binds agent automations (not handled by the platform yet).** Every `agentTurn` automation stores an `inferenceBinding` (`cron_jobs.job_json` in the state database) whose `authorizationId` is derived from the profile's `authorizationLifetimes` entry, and `paste-api-key` issues a new one even for identical bytes. After a key save, each automation bound to that profile fails with "Automation inference account was replaced. Explicitly select an authorized account again." and is auto-disabled after 10 consecutive failures; Doctor only adopts an account for jobs with no binding, so a restart does not heal it. Rebind on the running instance: `openclaw automations edit <id> --model '<provider>/<model>@<profile>'` (an explicit `model@profile` is the only thing that re-captures the binding), then `openclaw automations edit <id> --clear-model` (the pin goes, the binding stays), then `openclaw automations enable <id>` if it was auto-disabled. On a multi-agent instance a job without an `agentId` (the built-in Memory Dreaming Promotion) needs `--agent <default agent>` on both edits. After rotating a key, do this for every instance (2026-11-23: 26 automations on 10 instances).

**Primary model.** `agents.defaults.model.primary` is resolved per instance by `getPrimaryPin` in `services/gateway-store.ts`, most specific first: `gateways.primary_model` (Home card picks a model by name, provider implied via `providerForModel`) → `gateways.primary_provider` (older pin) → `org_members.primary_provider` (My API Keys) → `organizations.primary_provider` + `organizations.primary_model` (Admin → API Keys: provider select plus a model select limited to that provider; changing the provider clears the model). A model pin only counts when the member has a key for its provider; otherwise the generator falls back to the provider pin, then to `DEFAULT_PRIMARY`. The provider pick-lists in `PROVIDERS[].models` are deliberately short (Google: Gemini 3.8 Flash, which is `DEFAULT_PRIMARY`, then Gemini 4 Hydrogen, Neon and Argon; Token Kiosk: GPT-5.5 + Claude Sonnet 5 + MiniMax M3.1 Flash); the generator still declares the previously offered models (`retiredModels`: older kiosk ids) so old pins keep resolving, but they are not in `agents.defaults.models` or `modelPolicy.allow`. Taking a model off a pick-list therefore takes it off the allowlist, and OpenClaw fails every automation or session that names a model outside it ("automation model override … rejected by agents.defaults.modelPolicy.allow"): on 2026-11-27 Gemini 3.8 Flash was dropped for Gemini 4 Hydrogen for a few hours and two of Jun's automations failed until it was allowed again; Flash went back on the list as the default the same day. Automations carry such refs because the rebind recipe below writes one. So when a default is retired, list it in the provider's `formerDefaults` (none today): the generator keeps those in `agents.defaults.models` and `modelPolicy.allow`.

## Secret-store providers (Notion)

A provider with `kind: 'secret'` in `PROVIDERS` (today: `notion`, entry `NOTION_API_TOKEN`, host `api.notion.com`, skill `notion`) is a non-LLM credential. Its key uses the normal org/personal key plumbing but never reaches auth-profiles.json and is never a primary-provider candidate (`MODEL_PROVIDERS`). `ensureGatewaySecrets` in `services/gateway.ts` writes it into the running instance's OpenClaw secret store (`openclaw secrets store set … --allow-host …` exec'd in the container, value passed through a transient 0600 file in the data dir, then `secrets reload`) and records what it set in `<gatewayDir>/.clawhuddle-secrets.json`. Only then does the generator emit `skills.entries.<skill>.apiKey = {source:'store', id}` — OpenClaw refuses to start or reload on an unresolved store ref, so the ref follows the state file. It runs after deploy/restart (`scheduleSecretSync`), on status promotion to running, and on key changes. A same-named entry the member created themselves (no record of ours) is left untouched.

**gog OAuth client (`kind: 'oauth-client'`, provider `google-workspace`, org-level only).** The key is the Google Cloud `client_secret_….json`, validated by `parseGoogleOAuthClient` and shown by client id. gog keeps the client secret and members' refresh tokens in a file keyring whose password must be in the environment of every process using it, so `ensureGogEnv` adds `GOG_KEYRING_BACKEND=file` + a random `GOG_KEYRING_PASSWORD` to the instance's `env` file (sourced by the entrypoint) before deploy, restart or start, never changing a value already there. Once the instance is up, the sync runs `gog auth credentials set` (env sourced, client via a transient 0600 file) and records the fingerprint in `<gatewayDir>/.clawhuddle-gog.json`. An instance whose `gog/data/credentials.json` exists without that record is the member's own and is never touched. A running instance without the env settings shows `restart` on the API Keys page; it gets the client at its next restart or redeploy. Members still sign in with `gog auth add <email>`.

**Google sign-in from Home.** Each running instance card has a Google account section (`components/google-connect.tsx`) backed by `GET /gateways/:gatewayId/google` (readiness `ready` / `pending` / `restart` / `no-client` / `keyring`, plus connected accounts) and, for the instance's own member only (`requireGatewayAccess({ ownOnly: true })`), `POST …/google/start`, `POST …/google/finish` and `DELETE …/google/accounts/:email`. They drive gog's remote flow (`gog auth add <email> --remote --step=1|2`, services `GOG_SIGN_IN_SERVICES`) with the instance env sourced. The shared client is a Desktop OAuth client, which only allows loopback redirects, so Google ends on an `http://127.0.0.1:<port>/oauth2/callback?…` page that does not load; the member pastes that address back, it is validated as loopback with `code` and `state`, and handed to gog through a transient 0600 file, never on a command line or in a log.

## LLM usage (Admin → Usage)

`GET /api/orgs/:orgId/gateways/:gatewayId/usage?days=1|7|30|90` (own instance or admin+, running only) runs OpenClaw's `sessions.usage` gateway method in the container (`openclaw gateway call sessions.usage`, the same numbers as the Control UI's Usage tab) and `services/usage.ts` condenses it to `GatewayUsage`: totals, by model, by channel (`other` = no channel: cron, heartbeat, Control UI), per day, message/error counts. Session keys, titles and creators are dropped; nothing per person or per message leaves the container. Cost is OpenClaw's list-price estimate, not what Token Kiosk or Claw Proxy bill. Each read is a CLI run (~2–6 s), so at most 3 run at once, complete results are cached 5 min (`refresh=1` skips it), and an incomplete one (`cacheStatus` ≠ `fresh`: OpenClaw re-indexes transcripts in memory after every restart, so the first read after a boot returns zeros) is never cached.

**Nightly snapshot (since 2026-11-18).** The Admin → Usage page no longer reads instances live: it shows the org's latest snapshot from `GET /api/orgs/:orgId/usage/snapshot` (owner/admin), one row per org in `usage_snapshots` (only the latest is kept). `startUsageSnapshotScheduler` (started in `index.ts`) checks every 5 min and, between 01:00 and 05:59 in `USAGE_TIME_ZONE` (default `Asia/Singapore`, UTC+8), snapshots every org whose snapshot isn't for today's local date: for each running instance, three `sessions.usage` runs (`mode: specific`, `timeZone`), one per scope in `USAGE_SCOPES`: `7d`, `30d`, `month`. Each scope ends on the last complete local day; `month` is the 1st of that day's month, so the 1st's snapshot holds the whole previous month. An incomplete answer is retried after 10/20/40 s. `POST …/usage/snapshot` ("Snapshot now") takes one in the background (~1 min for 16 instances). The per-instance live route above is no longer used by the web app.

## Config Generation

`apps/api/src/services/openclaw-config.ts`:
- `generateOpenClawConfig()` — creates full `openclaw.json` from options
- `mergeOpenClawConfig()` — updates platform-managed fields while preserving user customizations

Platform-managed fields: `meta`, `gateway.*`, `models.providers.*` (custom providers), `agents.defaults`, `channels`, `plugins`.

Slack `streaming` (threaded progress card with tool rows) and `replyToModeByChatType` (`all`) are platform defaults written onto an existing Slack block only while it holds a value the platform wrote (`SLACK_STREAMING_HISTORY`) or none; a value the member set is kept across redeploys (Kony uses the Block Kit card without tool rows since 2026-11-04).

`agents.defaults` is rewritten wholesale on every merge. Besides the model lists it carries `thinkingDefault: low`, `toolProgressDetail: raw` and, since 2026-11-10, `heartbeat.isolatedSession: true`: OpenClaw otherwise runs the 30-minute heartbeat in the main session and replays its full history each tick. That key exists only until an instance's first boot on OpenClaw 2026.11.5+, where the heartbeat is an automation: Doctor converts `agents.defaults.heartbeat` and `agents.entries.<id>.heartbeat` into a job ("heartbeat-main" on an upgraded instance, "Proactive check (main)" on a new one: isolated, every 30 min, idle only), removes the keys and stamps `meta.lastTouchedVersion`; from then on the schema refuses the key ("agents.defaults: Unrecognized key: heartbeat": config reloads and most CLI commands stop). So once `lastTouchedVersion` is 2026.11.5 or later (`heartbeatConfigRetired`) the merge no longer writes it and removes a block that is exactly the platform's own; any other leftover is one Doctor could not convert and stays for the member. Two exceptions. `systemAgent` (OpenClaw's own: the agent that owns operations without an explicit one on a multi-agent instance, written by Doctor) is kept as found. And `heartbeat`: keys a member set in `agents.defaults.heartbeat` (e.g. Michael's `every: 0m`) are kept and the platform's `isolatedSession` only fills a missing key; a member's `agents.entries.<id>.heartbeat` also overrides it per key.

**Platform instructions (since 2026-11-13).** `services/platform-instructions.ts` renders a short note for the agent (Notion is already connected: don't `ntn login` or ask for a token; Google goes through `gog`, connect from the Home card) from what the instance really has, and `writePlatformInstructions` in `services/gateway.ts` writes it to `<workspace>/.clawhuddle/AGENTS.md` on every config write and after each secret sync. The generator adds `hooks.internal.entries.bootstrap-extra-files = {enabled: true, paths: ['.clawhuddle/AGENTS.md']}` (no master flag, so it is an allowlist of one: no other bundled hook is switched on), and OpenClaw loads the file into each new session next to the member's own AGENTS.md, which stays theirs. Scheduled runs load it too, and it carries one note they depend on: OpenClaw 2026.11.5+ asks every scheduled run to record a result (`automations` action `record_result`), Code Mode hides that tool's fields, and Gemini Flash guesses `status` where the field is `outcome`; the call fails, and a failed tool call in a run that ends with `NO_REPLY` marks the whole run failed ("⚠️ Automations failed"; 10 in a row disable the automation). The "Scheduled runs" section gives the exact call (2026-11-28: 3 of 4 quiet runs failed on Sandworm without it, 8 of 8 passed with it). The merge only joins our path to the list the member's entry already uses, and leaves hooks alone when they are off, our hook is disabled, or the member relies on open-ended discovery.

Three more blocks are platform defaults since 2026-11-02 and are overlaid key by key (`overlayBlock`), so whatever else a member keeps in them survives a redeploy: `messages` (Slack inbound quiet window 3 s, queue mode `collect`, Slack debounce 3 s — short bursts become one turn), `session.dmScope = per-channel-peer` (one DM session per Slack peer), and `secrets.egressProxy.enabled = true` (secret-store entries reach exec as sentinels, swapped in only on hosts bound with `openclaw secrets store set NAME --allow-host <host>`; HTTPS to other hosts is unrestricted unless the member sets `allowedHosts`; plain `http://` to non-loopback hosts is refused).

The API Keys pages show where each instance stands: `GET /api/orgs/:orgId/api-keys/secret-status` (admin) and `/me/api-keys/secret-status` (own instances) return one `SecretStatusEntry` per gateway with `secrets.<provider>` = `injected` (our fingerprint is in the state file) / `pending` (key exists, store not written yet; done once the instance is running) / `member` (state file records `null`: the member's own entry, never overwritten) / `none`. Computed by `secretStatusFor` in `services/gateway.ts`; the web hook `lib/use-secret-status.ts` repolls every 10 s while a running instance is `pending`.

## Hermes runtime (since 2026-11-28)

A second runtime for an instance: Hermes Agent (Nous Research), image `clawhuddle-hermes:local` built by the compose service `hermes-base` from `docker/hermes/Dockerfile` (`FROM nousresearch/hermes-agent:v0.23.5` plus `/opt/clawhuddle/helper.py`; override with `HERMES_IMAGE`). Upstream ships several releases a week: an instance changes version only when the tag is bumped, `hermes-base` is rebuilt and the instance is redeployed. Slots, limits, naming, tokens, subdomains, `gateway_channels` and model pins are the same as for OpenClaw. `gateway.ts` owns the lifecycle and branches on `g.runtime`; the Hermes side is `services/hermes.ts` (files, container, in-container calls) and `services/hermes-config.ts` (pure: what goes into the files). The dockerode helpers both runtimes use are in `services/docker.ts`.

- **Org switch.** `organizations.hermes_enabled` (Admin → API Keys → Agent runtimes; owner/admin). While off, creating a `hermes` instance answers 403 `runtime_disabled`; turning it off leaves existing Hermes instances alone.
- **Two directories per instance.** The home, `data/gateways/<org>/<user>[-N]` → `/opt/data` (uid 10000), is the member's: `config.yaml`, `.env`, sessions, skills, workspace. It is seeded once (`seedHermesConfig`); afterwards the platform writes only its skills category and the Google client file there. The managed layer, `data/gateways/<org>/.hermes/<user>[-N]` → `/etc/hermes` read-only (Hermes's managed scope, `HERMES_MANAGED_DIR`), holds `.env` (LLM keys, channel tokens, `NOTION_API_KEY`; 0640 root:10000), `config.yaml` (written as JSON: `model`, `fallback_providers`, `providers.tokenkiosk` / `providers.claw`, `dashboard.trusted_proxies`) and `clawhuddle-state.json` (0600 root). `syncHermesFiles` rewrites it wholesale; Hermes applies it over the member's files, so there is no merge and no per-key ownership record: whatever the member keeps in the home stays, and platform values win where both set one.
- **Keys and model are live.** Hermes re-reads the managed files every turn: a changed key or model pin (`regenerateGatewayConfig` → `syncHermesFiles`) is used by the next turn without a restart. No auth store, no authsave container, no automation rebind. A removed key is the exception: a running instance keeps it in its process environment until the next restart. A change to channel tokens redeploys the instance.
- **Models.** `PROVIDERS[].hermes` maps a provider to Hermes's provider name and env var (google → `gemini` / `GOOGLE_API_KEY`, token-kiosk → `custom:tokenkiosk`, claw-proxy → `custom:claw`, anthropic, openai, openrouter); a provider without a mapping (OAuth credentials) is not offered to Hermes instances. The pin rule is OpenClaw's (`resolvePrimaryModel`), except that without a Google key the first provider with a key is the primary. One fallback entry per other provider. Two things Hermes is strict about where OpenClaw is not: a fallback naming a model the provider no longer has stops the turn (so a key's `default_model` that is not on the provider's pick-list is ignored), and as a fallback a `gpt-5.x` id on a named custom provider is sent to `/v1/responses` unless the provider block declares `api_mode: chat_completions` (it does). The kiosk's `max_completion_tokens` clamp does not hit Hermes. The model of a Hermes instance is picked in ClawHuddle (Home card, API Keys), not in the Hermes dashboard: the managed layer pins `model`, so the dashboard's "Switch model" answers ok and changes nothing. Each custom provider block also declares the provider's pick-list as `models` with `discover_models: false` (plus an older pin the instance still runs on): the dashboard lists a saved endpoint's models from that block only, and without it shows "0 models".
- **Dashboard.** Port 9119 behind Traefik on the instance's subdomain. Sign-in is username = the subdomain, password = `gateways.token` (same release rules as the OpenClaw token; the Home card shows both). Hermes has no token-in-link login, so "Open dashboard" (Home card, and Admin → Members through the logged `/access`) goes to `https://<subdomain>.<GATEWAY_DOMAIN>/_clawhuddle/open#u=<username>&p=<token>` (`gatewayUrl` in `apps/web/lib/gateway-url.ts`): a static page the API serves (`routes/dashboard-open.ts`, public, no secret in it, hash-only CSP) that takes the login from the URL fragment, removes it from the address and history, makes the dashboard's own `POST /auth/password-login` call and lands on `/`. It runs on the instance's origin because each Hermes container carries a second Traefik router, `<container>-open` (`Host(…) && Path(/_clawhuddle/open)` → `api@docker`, override `API_TRAEFIK_SERVICE`; `createTraefikLabels(…, { openPage: true })`); labels are set at container create, so an instance deployed before 2026-11-28 gets it at its next Redeploy and until then the link ends on Hermes's own sign-in page. A fragment is never sent to a server, so the token is in no access log (OpenClaw's `/?token=` link is). Local dev has no Traefik: the link is the bare address and the login is typed. The container `Env` carries only a scrypt hash of the token and a session secret derived from it (`hermesDashboardEnv`), never the token. `dashboard.trusted_proxies` is the gateway network's subnets, recorded at deploy (Hermes reads it once at start): without it Hermes ignores `X-Forwarded-Proto` and issues session cookies without `Secure`. `/api/status` is unauthenticated in Hermes by design (version, memory, gateway state; no credentials) and is what `checkHermesHealth` reads.
- **Skills.** Org skills and two platform skills (`clawhuddle-platform`: what the instance already has; `notion`, only with a Notion key) go to `skills/clawhuddle/` in the home, each platform one marked `.clawhuddle-managed`; only that category is ever cleaned. There is no always-loaded platform note as on OpenClaw.
- **Notion and Google.** No secret store and no egress proxy on Hermes: the Notion key is a plain env var. Hermes hides provider keys from the agent's terminal; `NOTION_API_KEY` reaches it because our `notion` skill declares it. `secrets.notion` is `injected` / `pending` / `none`. The org's `google-workspace` client JSON is written by the API as the bundled google-workspace skill's client file (`hermesGoogleClientFile`; a client file without our record in the state file is the member's and is left alone). Sign-in from Home uses the same routes as OpenClaw; `helper.py google-start|google-finish|google-revoke` drive the skill's setup script, the redirect is `http://localhost:1`, and an instance holds one Google account (`RUNTIME_FEATURES.hermes.multiGoogleAccounts = false`).
- **Channels.** Unknown DMs get a pairing code (`hermes pairing approve`, codes validated with `HERMES_PAIRING_CODE`); the list shows who is waiting, not the codes. Hermes has no device pairing: the Device Requests routes skip Hermes instances.
- **Usage.** `helper.py usage <start> <end> <tz>` reads `state.db` read-only and prints aggregates only; `condenseHermesUsage` maps them to `GatewayUsage` with the platform's provider names (`platformProviderName`). Sessions are bucketed by start time. Cost is Hermes's estimate; a model it has no price for (kiosk `azure/gpt-5.5`) counts under `missingCostEntries`. The answer is always `fresh`.
- **Container.** `Cmd ['gateway','run']`, 4 GiB memory limit, 1 GiB shm, restart `unless-stopped`; about 460 MiB idle, about 10 s to boot, `docker stop` is clean. One-shot agent turn for a test: `docker exec -u hermes -w /opt/data/workspace <container> hermes chat -Q -q '<prompt>'`; the agent log is `/opt/data/logs/agent.log`.

# Local dev
